# HXC-162 / HXC-163 — skills subsystem wiring and registration

QA evidence run (§11.4.83) for two defects in which HelixCode's skills subsystem
was present, correct and documented in source, yet completely dead at runtime.

- **HXC-162** — the skill dispatcher was constructed at `cmd/cli/main.go:1060`
  and immediately discarded into `_`, so no user input could ever trigger a skill
  in the interactive CLI.
- **HXC-163** — none of the seven shared governance skills were registered with
  the running system, and `skills/media-validator` was a tracked symlink to a
  macOS `/Volumes/T7` path that cannot resolve on this Linux host.

Both are the §11.4.108 SOURCE-vs-RUNTIME gap: reading the source, you would
conclude the feature worked.

## Runtime signatures (§11.4.108)

Each item is proven by ONE machine-checkable observable that is never a re-grep
of the source.

**HXC-162** — `TestSkillAutoTrigger_WiredIntoInteractiveREPL`
(`helix_code/cmd/cli/skill_autotrigger_wiring_test.go`). It drives the REAL
startup path (`c.ensureSubsystems`, which is what `main()` calls at
`main.go:1393`) and the REAL REPL (`handleInteractive`) over a real stdin pipe,
with a recording `llm.Provider` in place of a network provider. The assertion is
on the prompt that ACTUALLY REACHES THE PROVIDER: it must be the matched skill's
rendered body with its named capture substituted, not the raw text typed. A
dispatcher object merely existing cannot satisfy this.

**HXC-163** — `TestGovernanceSkills_RegisteredAndInvocable`
(`helix_code/internal/commands/governance_skills_registered_test.go`). It builds
a `SkillLoader` with NO on-disk directories — the built-in tier only, exactly
what a freshly installed binary sees — and for each of the seven skills asserts
it resolves from `builtin:`, carries a description, that a real user utterance
routes to it through `FindMatching`, and that it renders a non-empty body
through the same path `/skills invoke` uses. Missing or unresolvable ⇒ FAIL,
never a silent skip.

Two supporting guards:

- `TestSkillsTree_NoDanglingOrHostAbsoluteSymlinks` — covers the on-disk skills
  tree the Go registry cannot see. Fails on a dangling symlink AND on any
  host-specific absolute target. The second assertion fixes the class rather
  than the instance: a link into `/Volumes/…` is unportable by construction even
  on a machine where it happens to resolve.
- `TestGovernanceSkills_BuiltinSetIsCurated` — pins the built-in tier to a small
  curated set. Registered skill count degrades agent selection accuracy through
  inter-skill shadowing, and the harm is behavioural, so a bulk import would not
  show up in any other test. This one fails loudly instead.

## How the RED evidence was captured (§11.4.115)

The RED files are not transcriptions. They were regenerated by checking out the
pre-fix commit into an isolated `git worktree` under `/tmp` (the shared working
tree was never touched), copying the two guard files in, and running them there.
The worktree needed `submodules/` symlinked in because `git worktree` does not
check out submodules — that is an environment artifact of the worktree, and the
initial `[setup failed]` output it produced was NOT treated as RED evidence.
The worktree was removed afterwards.

Reproduce:

```bash
# RED (defect reproduces on pre-fix code)
git worktree add --detach /tmp/hxc_prefix bbd236c9^
ln -sfn "$PWD/submodules" /tmp/hxc_prefix/submodules
cp helix_code/cmd/cli/skill_autotrigger_wiring_test.go /tmp/hxc_prefix/helix_code/cmd/cli/
cp helix_code/internal/commands/governance_skills_registered_test.go /tmp/hxc_prefix/helix_code/internal/commands/
cd /tmp/hxc_prefix/helix_code
go test -count=1 -run TestSkillAutoTrigger ./cmd/cli/                 # FAILS
go test -count=1 -run TestGovernanceSkills ./internal/commands/       # FAILS

# GREEN (at HEAD)
go test -count=1 -run TestSkillAutoTrigger ./cmd/cli/
go test -count=1 -run 'TestGovernanceSkills|TestSkillsTree' ./internal/commands/

# Polarity — these must FAIL at HEAD, proving the defect is gone
RED_MODE=1 go test -count=1 -run TestSkillAutoTrigger ./cmd/cli/
RED_MODE=1 go test -count=1 -run TestGovernanceSkills ./internal/commands/
```

The symlink guard's paired mutation (restore the absolute target, observe FAIL
on both the dangling and the host-absolute assertion, restore, observe PASS) was
run during the session and is reproducible with:

```bash

(cd helix_code && go test -count=1 -run TestSkillsTree ./internal/commands/)   # FAILS
```

## Symlink investigation (§11.4.124)

`skills/media-validator` was added by `1bc82267` (2026-06-21). The same commit
also rewrote a codegraph MCP path from `/run/media/…` to `/Volumes/T7/…`, which
shows it was authored on a macOS host with an external drive at `/Volumes/T7`;
the link was never valid in this checkout. It is generated by
`constitution/skills/*/register.sh`, which computes an ABSOLUTE `SCRIPT_DIR` and
runs `ln -sf "$SCRIPT_DIR"` — so the authoring host's path is baked in. Every
`register.sh` under `constitution/skills/` shares that pattern; media-validator
is simply the one whose link got committed.

It was NOT dead code: `constitution/mcp/media-validator-mcp.json` and the skill's
own documentation both invoke it through the repo-root path
`skills/media-validator/media-validator.sh`. Removing it would leave those
references pointing at nothing, so there was no proof it is unneeded and the
§11.4.124 removal branch did not apply. It was repaired to the relative target
`../constitution/skills/media-validator`, which resolves in every checkout on
every platform.

The generator itself still emits absolute paths, so a future re-run of
`register.sh` would reintroduce this. That generator lives in the constitution
submodule and was deliberately not modified here (CONST-051(B) decoupling); the
symlink guard will catch a recurrence.
