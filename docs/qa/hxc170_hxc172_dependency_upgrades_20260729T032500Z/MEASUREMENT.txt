5. THE DNS-REBINDING SETTING — VERIFIED EXPLICITLY, NOT ASSUMED
================================================================================

HXC-172 asked for the protective setting to be "explicitly verified as enabled
in our configuration rather than assumed". Verified, and the finding is negative
in an instructive way:

  (a) The SDK is never imported, so its DNS-rebinding-protection default does
      not exist in our runtime. It cannot be "turned on". Upgrading to 1.24.0+
      would close the Dependabot alert while changing nothing we actually run.

  (b) Our SSE path does not use the SDK transport at all — src/index.ts
      runSSE() hand-rolls http.createServer, and sets
      'Access-Control-Allow-Origin': '*' at lines 145 and 169 with NO Origin
      validation and NO Host validation anywhere. That is the same
      vulnerability class the advisory describes, in OUR code, where no SDK
      upgrade reaches it.

  (c) runSSE() is not reachable as deployed. Dockerfile CMD is
      ["node","dist/index.js"] with no args; the code reads NO environment
      variables at all (so ENV MCP_PORT=9100 is inert); defaultConfig.transport
      is 'stdio'; and compose adds no command/entrypoint override. SSE is only
      reachable via an explicit --transport sse argument that nothing supplies.

  Consequence worth its own item: the container publishes 9100 and HEALTHCHECKs
  wget http://localhost:9100/health, but nothing ever listens there — the
  healthcheck cannot pass. Even in SSE mode the port would default to 7062,
  because MCP_PORT is never read.
